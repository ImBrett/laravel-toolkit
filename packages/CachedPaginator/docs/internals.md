# How It Works

Cached Paginator keeps page data fresh while avoiding repeated `COUNT(*)` queries. Understanding the internal flow helps you tune performance for your workloads.

## Cache Keys

1. Take the underlying SQL generated by the query builder.
2. Append the bound parameters (JSON encoded).
3. Hash the combined string with MD5.
4. Compose the final key as `prefix:table:hash`.

The prefix comes from (in order of precedence):

1. `cachedPaginationPrefix()` model method, if present.
2. `$cachedPaginationPrefix` property.
3. `config('cached-paginator.prefix')`.

## TTL & Threshold

- **TTL** – if zero or negative, caching is skipped and the builder falls back to the default behaviour.
- **Threshold** – totals lower than the threshold are not cached. Handy to avoid caching noise on small datasets.

Both values can be dynamic via model methods.

## Execution Pipeline

```mermaid
flowchart TD
    A[paginate()] --> B{Total provided?}
    B -- yes --> C[Defer to parent paginate()]
    B -- no --> D[Resolve page & perPage]
    D --> E[calculateTotalCount()]
    E --> F{TTL > 0?}
    F -- no --> G[countForPagination()]
    F -- yes --> H[cachedCount()]
    H --> I{Hit?}
    I -- yes --> J[Reuse cached total]
    I -- no --> K[countForPagination()]
    K --> L{total >= threshold?}
    L -- yes --> M[Cache::put()]
    L -- no --> N[Skip caching]
    J & K & M & N --> O[Resolve results]
    O --> P[Build paginator]
```

## Invalidation

Since caching is time-based, totals refresh automatically when the TTL expires or when the query changes (different filters, joins, user-specific conditions).

To invalidate on demand, call `Cache::forget($key)` with the key generated by `CachedPaginatorBuilder::makeCacheKey()`. A convenient approach is to dispatch a model event listener that deletes relevant prefixes when critical data mutates.
